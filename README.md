# Zero-Trust API Gateway

두 부분으로 된 프로젝트입니다.

1. **게이트웨이와 인증 서비스.** 모든 요청을 입구에서 검증하는 API Gateway를 Spring Boot로 직접 구현했습니다. Spring Cloud Gateway나 Spring Security의 인증 기능을 쓰지 않고 토큰 검증 필터, 권한 검사, 요청 제한, 리버스 프록시를 손으로 만들었습니다.
2. **배포 파이프라인.** 그 서비스가 배포되는 길을 다시 만들었습니다. 다른 사람이 승인한 변경만 배포되고, 누가 무엇을 승인해 무엇이 올라갔는지 기록이 자동으로 남습니다. 만든 뒤에는 그 절차를 직접 건너뛰어 보고 막히는지 확인했습니다.

## 배포 파이프라인

### 왜 만들었나

처음 만든 배포는 push하면 테스트와 보안 검사를 거쳐 서버까지 자동으로 올라가는 방식이었습니다. 돌아가기는 했지만 두 가지가 없었습니다. **승인한 사람이 없었고, 배포 기록이 없었습니다.** 지금 서버에서 도는 것이 누구의 어떤 변경인지 답하려면 커밋 기록과 CI 화면을 사람이 맞춰 봐야 했습니다.

그래서 금융권처럼 변경을 통제해야 하는 조직을 가정하고, 빠진 부분을 만들었습니다. 증명하려는 명제는 하나입니다.

> 승인받은 변경과 실제 배포된 변경이 같다.

| 요구 | 이 프로젝트에서 하는 일 |
|---|---|
| 결재 | 올린 사람과 승인한 사람이 달라야 배포됩니다 |
| 증적 | 배포 한 건마다 요청자, 승인자, 커밋, 검사 결과, 실제 이미지를 이어서 기록합니다 |
| 접근 제어 | CI에 오래 쓰는 키를 저장하지 않고, 필요한 작업만 임시 권한을 받습니다 |

### 흐름

```
코드 저장소                 배포 설정 저장소                          클러스터
───────────                ─────────────────                        ────────
push
 └ 테스트, 정적 분석,
   비밀값 탐지
 └ 이미지 빌드
 └ 취약점 검사
        │
        │ 이미지 다이제스트
        ▼
                           변경 요청: 값 파일의 다이제스트 한 줄
                            └ 이 이미지가 검사를 통과한 것인가
                            └ 오늘 기준으로 다시 취약점 검사
                            └ 배포 요청서 작성
                           다른 사람이 승인 → 합치기
                            └ 보호 설정이 기대값과 같은가
                            └ 승인자가 올린 사람과 다른가
                            └ 승인 뒤에 얹힌 커밋은 없는가
                            └ 이미지 검사 한 번 더
                            └ deployed 브랜치 이동, 증적 기록
                                        │
                                        ▼
                                                    ArgoCD가 deployed를 따라 반영
```

합치는 것이 곧 배포는 아닙니다. 합친 뒤의 검사를 통과해야 `deployed` 브랜치가 옮겨지고, ArgoCD는 그 브랜치만 봅니다. 검사에 걸린 변경은 main에 남지만 배포되지 않습니다.

### 저장소 셋

| 저장소 | 담는 것 |
|---|---|
| [zero-trust-gateway](https://gitlab.com/bkn06210-lab/zero-trust-gateway) | 이 저장소. 서비스 코드와 이미지를 만들고 검사하는 CI |
| [zero-trust-deploy](https://gitlab.com/bkn06210-lab/zero-trust-deploy) | 무엇을 배포할지. Helm 차트와 값 파일. 커밋 이력이 배포 이력입니다 |
| [zero-trust-pipeline](https://gitlab.com/bkn06210-lab/zero-trust-pipeline) | 배포를 어떻게 검사할지. 검사 절차, 기대 보호 설정, Go로 만든 검사 도구 `deployctl` |

검사 절차를 따로 뺀 것은 처음 설계가 아니라 사고를 겪은 뒤의 결정입니다. 아래 "겪은 문제"의 첫 번째입니다.

### 만든 것

- **검사 도구 `deployctl`.** Go로 만든 CLI입니다. 이미지 검사, 승인 검사, 보호 설정 대조, 증적 기록, 돌고 있는 서비스에서 커밋과 승인자까지 거꾸로 찾는 역추적, 배포 요청서 작성, 배포 뒤 판정을 합니다.
- **다이제스트로 배포.** 이미지는 코드 저장소에서 한 번만 만들고, 이후 모든 단계가 태그가 아니라 다이제스트로 같은 이미지를 가리킵니다.
- **Docker 데몬 없는 CI.** 이미지는 BuildKit rootless로 만들고, 통합 테스트는 러너가 띄워 주는 PostgreSQL과 Redis에 붙습니다. CI 작업이 특권 모드 컨테이너를 요구하지 않습니다.
- **저장된 키 없는 AWS 권한.** GitLab이 작업마다 발급하는 증명서로 AWS 역할을 받습니다. AWS 쪽 조건은 이 프로젝트의 main 브랜치입니다.
- **배포 키로만 움직이는 `deployed`.** 합친 뒤 검사를 통과한 파이프라인이 배포 키로 옮깁니다.
- **매일 재검사.** 지금 배포되어 돌고 있는 이미지를 그날의 취약점 목록으로 하루 한 번 다시 검사합니다.
- **승인자를 돕는 배포 요청서.** 두 이미지 사이의 코드 변경을 Claude API가 읽고 무엇이 바뀌었고 어디가 위험한지 적습니다. 값 파일 외에 바뀐 파일과 되돌리는 배포인지는 모델을 거치지 않고 사실로 적습니다. 요청서는 참고 자료이고 검사는 요약과 무관하게 동작합니다.

### 직접 뚫어 본 결과

통제를 만들 때마다 바로 그 통제를 건너뛰어 봤습니다.

| 시도 | GitLab 무료 설정만으로 | 검사를 붙인 뒤 |
|---|---|---|
| 승인 없이 합치기 | 합쳐진다 | 막힘. `deployed`가 움직이지 않는다 |
| 본인이 올린 것을 본인이 승인 | 승인도 되고 합쳐진다 | 막힘 |
| 승인받은 뒤 커밋을 더 얹기 | 승인 표시가 유지된 채 합쳐진다 | 막힘. 승인 33초 뒤에 올라온 커밋을 잡음 |
| 취약점 검사 작업이 없는 파이프라인의 이미지 | 파이프라인은 성공으로 표시 | 막힘 |
| 다이제스트와 커밋을 서로 다른 것으로 적기 | | 막힘 |
| 클러스터를 손으로 직접 고치기 | | 3초 안에 되돌아감 |
| 기능 브랜치에서 운영 AWS 역할 요청 | | AWS가 거부 |
| 브랜치 보호를 풀고 배포 | | 막힘. 설정이 기대값과 다르다고 실패 |
| `deployed`에 사람 계정으로 직접 push | | **뚫림.** 아래 한계 참고 |

### 겪은 문제

만든 것이 초록색으로 도는데도 틀려 있던 경우들입니다. 전체 과정은 [트러블슈팅 기록](docs/TROUBLES.md)에 있습니다.

**승인 검사를 지우는 변경이 승인을 받고 합쳐져, 8시간 동안 검사가 꺼진 채 배포가 나갔습니다.**
우회 시도용으로 올려 둔 변경 요청을 다른 것들과 함께 승인하고 합쳤습니다. 승인 절차는 지켜졌는데 내용이 통과한 것입니다. 원인은 검사 절차가 검사받는 저장소 안에 있었다는 점입니다. 같은 저장소에 규칙을 더해도 그 규칙을 같이 지울 수 있어서, 검사 절차를 별도 저장소로 옮겼습니다. 같은 종류의 변경을 다시 올려 더는 통하지 않는 것을 확인했습니다.

**7주 전에 취약점 검사를 통과한 이미지를 다시 검사하니 HIGH 9건이 나왔습니다.**
이미지는 한 글자도 바뀌지 않았습니다. 9건 모두 이미지를 만든 다음 날 이후에 공개된 취약점이었습니다. 검사 통과는 이미지의 성질이 아니라 그날의 사실이었습니다. 배포할 때 그날 기준으로 다시 검사하고, 돌고 있는 이미지는 매일 검사하게 했습니다.

**배포로 파드를 교체할 때마다 요청 몇 건이 접속에 실패했습니다.**
교체하는 동안 초당 열 건쯤 요청을 보내 보니 세 번 다 실패가 나왔습니다. 201건 중 2건, 400건 중 6건, 402건 중 3건입니다. 배포는 매번 성공으로 표시됐습니다. 실패가 교체 직후 3초에 몰려 있는 것을 보고, 옛 파드가 요청을 넘겨받는 목록에서 빠지기 전에 먼저 꺼지는 것이 원인임을 찾았습니다. 꺼지기 전에 10초를 기다리게 한 뒤 464건, 466건, 466건 모두 실패 0건이었습니다.

**뜨지 못한 배포가 증적에는 배포된 것으로 남았습니다.**
DB 포트를 틀리게 고친 변경이 모든 검사를 통과했습니다. 새 파드는 계속 재시작했지만 옛 파드가 요청을 받아 사용자는 멀쩡했고, 기록에는 배포됐다고 적혔습니다. 배포 전 검사로는 알 수 없는 문제라, ArgoCD 상태를 읽어 배포한 커밋이 정상으로 떴는지 판정하는 명령을 만들었습니다.

**서명 키를 바꿨는데 아무 일도 없다가, 상관없는 배포에서 인증이 전부 깨졌습니다.**
파드는 뜰 때 비밀값을 한 번만 읽습니다. 키를 바꾼 뒤 gateway만 다시 뜨자 두 서비스의 키가 어긋나 인증이 필요한 요청이 전부 401이 됐습니다. 바꾼 시점과 터지는 시점이 떨어져 있는 것이 문제여서, 비밀값을 바꿀 때 변경 요청으로 숫자 하나를 올리면 두 서비스가 함께 다시 뜨게 했습니다.

**AI 요약을 채점하다가 정답지가 틀린 것을 찾았습니다.**
위험한 변경 8개와 문제없는 변경 6개를 세 번씩 돌려 채점했습니다. 위험한 변경은 24번 중 24번 짚었고, 문제없는 변경에 잘못 경고한 것은 없었습니다. 처음에 틀린 것으로 채점된 한 문제는 모델이 아니라 직접 만든 정답이 틀린 것이었습니다. 문제 수가 적다는 것을 포함한 한계는 [평가 문서](docs/AI_SUMMARY_EVAL.md)에 적었습니다.

### 한계

- **`deployed`에 사람 계정으로 push가 됩니다.** GitLab은 보호 브랜치에 배포 키를 허용하면 그 키를 만든 계정에도 권한을 줍니다. 키를 등록하는 계정을 사람이 쓰는 계정과 분리해야 하는데 하지 않았습니다.
- **무료 요금제라 승인을 합치기 전에 강제하지 못합니다.** 그래서 합친 뒤에 검사하고 `deployed`를 옮기는 구조가 됐습니다. 걸린 변경은 main에 남고, 이전 상태로 되돌리는 변경을 승인받아 합쳐야 다시 진행됩니다.
- **배포가 실제로 떴는지는 파이프라인이 확인하지 못합니다.** 클러스터가 PC에 있어 GitLab의 러너가 닿지 않습니다. 판정 명령은 클러스터에 닿는 곳에서 사람이 돌려야 합니다.
- **비밀값은 변경 요청 밖에서 바뀝니다.** 누가 언제 바꿨는지 기록이 없습니다.
- **두 변경 요청을 거의 동시에 합치면** 한쪽의 증적이 남지 않을 수 있습니다.
- **재검사는 예전 버전으로 되돌리는 배포도 막습니다.** 예외로 통과시키는 길을 만들지 않았습니다.
- **특권 모드를 꺼 둔 러너에서의 동작은 확인하지 못했습니다.** gitlab.com이 제공하는 러너는 그 자체가 특권 모드로 돕니다.
- **클라우드의 쿠버네티스에는 올리지 않았습니다.** 클러스터는 PC의 kind입니다.

## 게이트웨이와 인증 서비스

### 왜 만들었나

인증과 권한은 거의 모든 서비스에 있지만, 대부분 라이브러리 설정 몇 줄로 끝나서 안에서 무슨 일이 일어나는지 모른 채 쓰게 됩니다. 토큰이 어떻게 검증되는지, 탈취되면 무슨 일이 생기는지, 왜 어떤 요청은 401이고 어떤 요청은 403인지를 설정이 아니라 코드로 이해하고 싶었습니다.

- **직접 만든다.** 기성 게이트웨이와 인증 프레임워크를 쓰지 않고 필터와 검증 로직을 손으로 씁니다. 암호화 알고리즘처럼 직접 만들면 안 되는 것은 검증된 라이브러리를 씁니다.
- **입구에서 전부 의심한다.** 클라이언트가 보낸 헤더도, 내부 서비스로 가는 요청도 믿지 않습니다. 열어 줄 것만 적고 나머지는 닫습니다.
- **돌아가는 것까지 책임진다.** 컨테이너, CI 보안 게이트, 클라우드 배포, 대시보드까지 만듭니다.

### 구조

```
클라이언트 ──▶ gateway :8080 ──▶ auth-service :8081 ──▶ PostgreSQL
                 │  1. 로그인 요청 제한 (Redis)              │
                 │  2. JWT 검증 → 401                     │
                 │  3. 역할 검사 → 403                     │
                 │  4. 신원 헤더 붙여 전달                   │
                 └──▶ Redis
```

바깥으로 열린 포트는 gateway의 8080 하나입니다. auth-service, PostgreSQL, Redis는 컨테이너 내부 네트워크에서만 통합니다.

| 서비스 | 역할 |
|---|---|
| **gateway** | 로그인 요청 제한, JWT 검증, 역할 기반 접근 제어, 뒤쪽 서비스로 요청 전달 |
| **auth-service** | 회원가입, 로그인, access/refresh 토큰 발급과 회전과 폐기, 관리자 API |

### 인증
- 비밀번호는 BCrypt 해시로만 저장합니다.
- 로그인 실패 시 "이메일 없음"과 "비밀번호 틀림"을 구분하지 않습니다. 응답 시간으로도 구분되지 않도록 없는 이메일에도 같은 해시 연산을 수행합니다.
- BCrypt 계산은 CPU 개수만큼만 동시에 돌립니다. 1초 안에 자리를 얻지 못한 요청은 계산하지 않고 503과 Retry-After로 거절합니다. 없는 이메일에도 해시를 돌리는 결정의 대가를 부하 실험으로 잰 뒤에 넣은 제한입니다.
- access token은 1시간짜리 JWT입니다. 사용자 id, 역할, 만료, 고유 번호만 담고 개인정보는 넣지 않습니다.
- refresh token은 32바이트 난수입니다. 서버에는 SHA-256 해시만 저장하고, 쓸 때마다 폐기 후 재발급합니다. 폐기된 토큰이 다시 오면 탈취로 보고 해당 사용자의 토큰을 전부 폐기합니다.

### Gateway
- 토큰 없이 열어줄 경로만 "메서드 + 경로" 정확 일치로 적는 허용 목록입니다. 기본은 전부 차단입니다.
- 서명, 만료, 필수 클레임을 검증합니다. 서명을 비운 토큰, 다른 키로 서명한 토큰, 내용을 바꾼 토큰을 모두 차단합니다.
- 클라이언트가 직접 쓴 신원 헤더는 버리고, 검증된 값으로 `X-User-Id`와 `X-User-Role`을 다시 써서 전달합니다.
- `/admin/` 아래는 ADMIN만 들어갑니다. 인증 실패는 401, 권한 없음은 403입니다.
- 로그인 요청은 1분 창에서 IP 30회, 이메일+IP 5회, 이메일 20회로 제한합니다. 한 기준에서 막힌 요청은 나머지 카운터를 올리지 않습니다. Redis Lua 스크립트로 INCR과 EXPIRE를 원자적으로 실행하고, 로그인에 성공하면 이메일 쪽 카운터를 지웁니다.
- 뒤쪽 서비스 호출에 시간 제한을 두고, 연결 실패 시 502를 돌려줍니다.

### 검증
- 통합 테스트 36건과 단위 테스트 6건이 있습니다. 통합 테스트는 실제 PostgreSQL과 Redis에 붙습니다. PC에서는 Testcontainers가 띄우고, GitLab CI에서는 러너가 작업 옆에 띄워 줍니다.
- gateway 테스트는 가짜 뒤쪽 서버를 두어 무엇을 전달했는지, 차단 시 정말 전달하지 않았는지까지 확인합니다.
- 같은 이메일 가입 50건과 같은 refresh 토큰 갱신 20건을 동시에 보내는 동시성 테스트가 있습니다.
- 배포한 서버에 로그인 요청을 초당 60건까지 보내 한계와 개선 효과를 쟀습니다. 예상을 먼저 적고 결과와 비교했습니다. [부하 실험 기록](docs/LOADTEST.md)

### GitHub Actions와 서버 배포
처음 만든 배포 경로입니다. push마다 아래가 순서대로 돌고, 앞 단계가 하나라도 실패하면 배포되지 않습니다.

| 단계 | 하는 일 |
|---|---|
| 테스트 | 기능이 깨졌는지 |
| Semgrep | 정적 분석(SAST). 코드를 실행하지 않고 위험한 패턴을 찾음 |
| gitleaks | 커밋 이력에 비밀값이 들어갔는지. 압축되어 내용이 안 보이는 Terraform 계획 파일과 상태 파일은 이름으로 막음 |
| Trivy | 이미지 안 라이브러리에 알려진 취약점이 있는지 |
| publish | 통과한 이미지를 GHCR에 올림. `latest`와 커밋 SHA 두 이름표 |
| deploy | AWS SSM 원격 명령으로 서버가 새 이미지를 받아 재시작. 공인 IP로 스모크 테스트 |

액션은 태그가 아니라 커밋 SHA로 고정했습니다.

### 인프라
`infra/`의 Terraform이 방화벽, SSH 키, 비밀값 저장소, IAM 역할, EC2 한 대를 만듭니다.

- 방화벽은 8080만 전체 공개하고 22는 관리자 IP에만 엽니다.
- 비밀값은 SSM Parameter Store에 암호화해 두고, 서버가 부팅할 때 IAM 역할로 읽어 `.env`를 만듭니다. 서버에 키를 두지 않습니다.
- 배포는 SSH 대신 SSM 원격 명령으로 하므로 GitHub에 22번을 열지 않습니다.
- 안 쓸 때는 `terraform destroy`로 전부 내리고 필요할 때 다시 올립니다.

### 관측성
Prometheus가 두 서비스의 지표와 서버 자원을 15초마다 수집하고, Grafana 대시보드가 실시간으로 보여줍니다.

- Gateway가 막은 요청을 사유별로 셉니다. 토큰 없음, 토큰 위조, 권한 없음, 로그인 제한.
- 지표는 별도 포트로만 내고 바깥에 열지 않습니다. 대시보드 포트는 관리자 IP에만 엽니다.
- 대시보드와 데이터 출처 설정은 파일로 저장소에 있어 서버를 다시 만들어도 그대로 올라옵니다.

### 겪은 문제

**동시에 갱신하면 성공 응답으로 이미 폐기된 refresh 토큰이 나갔습니다.**
동시 요청 테스트에서 응답은 200과 401로 정상이었는데, 직후 DB의 유효한 토큰이 0개였습니다. 늦게 처리된 요청이 이미 폐기된 토큰을 탈취로 판정해 먼저 성공한 요청의 새 토큰까지 폐기한 것입니다. 브라우저 탭 두 개 수준인 동시 2건에서도 매번 재현됐습니다. 폐기 시각을 기록하고 10초 유예를 두어 해결했습니다. [자세히](docs/TROUBLES.md)

**DB 연결 풀 고갈을 고쳤더니 로그인 성공률이 37%에서 26%로 떨어졌습니다.**
로그인 요청을 초당 60건까지 보내는 실험에서 DB 연결 10개가 전부 묶였습니다. 원인인 OSIV를 끄자 연결 문제는 사라졌지만 성공률은 더 떨어졌습니다. 연결 풀이 우연히 BCrypt 동시 실행 수를 10개로 묶어 주고 있었던 것입니다. BCrypt를 CPU 개수만큼만 동시에 돌리고 넘치는 요청은 1초 안에 거절하도록 바꾸자, 정상 응답이 49%로 오르고 응답 시간 중앙값이 5.18초에서 1.17초로 줄었습니다. [자세히](docs/LOADTEST.md)

**CI 이미지 스캔이 CRITICAL 4건을 잡았는데, 최신 Spring Boot로 올려도 고쳐지지 않았습니다.**
Tomcat 인증 우회 3건을 포함한 14건이었습니다. Boot 최신 패치의 의존성 목록을 확인하니 고쳐진 Tomcat 버전을 아직 쓰지 않고 있었습니다. Boot가 관리하는 버전을 개별로 덮어써서 해결했습니다. [자세히](docs/TROUBLES.md)

### 한계

- **전 구간 평문 HTTP입니다.** 토큰이 평문으로 지나갑니다. TLS 종료가 필요합니다.
- **HS256 대칭키입니다.** 발급과 검증이 같은 키를 공유합니다. RS256 공개키 방식으로 바꾸면 Gateway에 비밀키를 두지 않아도 됩니다.
- **뒤쪽 서비스가 `X-User-*` 헤더를 믿습니다.** 네트워크로 직접 접근을 막았지만, 내부 네트워크가 뚫리면 사칭이 가능합니다. 서비스 간 인증으로 보완할 수 있습니다.
- **access token은 만료 전 즉시 무효화가 안 됩니다.** 짧은 만료로 완화했고, `jti`로 블랙리스트를 붙일 수 있습니다.
- **IP를 `getRemoteAddr()`로 읽습니다.** 로드밸런서 뒤에서는 전부 같은 IP로 보입니다. 신뢰하는 프록시의 `X-Forwarded-For` 처리가 필요합니다.
- **IP가 여러 개인 요청 폭주는 로그인 IP 기준을 통과합니다.** 그때는 BCrypt 동시 실행 상한이 서버를 지키지만 정상 사용자의 로그인도 503을 받습니다. CAPTCHA나 WAF가 필요합니다.
- **GitHub Actions의 서버 배포 권한이 장기 키입니다.** 계정 정책이 OIDC를 막아 최소 권한의 전용 사용자로 대체했습니다. GitLab 쪽은 OIDC로 받지만 서버 배포는 아직 옮기지 않았습니다.
- **Grafana가 평문 HTTP입니다.** 관리자 IP에만 열려 있지만 로그인 비밀번호가 평문으로 지나갑니다. 도메인을 붙여 HTTPS로 올리면 해결됩니다.

## 실행

서비스만 띄우려면 Docker만 있으면 됩니다.

```bash
cp .env.example .env        # 값을 채웁니다. JWT_SECRET은 32바이트 이상
docker compose up -d --build
```

시연 스크립트로 동작을 확인할 수 있습니다.

```bash
bash scripts/p1-demo.sh     # 토큰 없음 401 / 위조 401 / 정상 200 / 신원 헤더 위조 무시
bash scripts/p2-demo.sh     # USER가 관리자 API → 403, ADMIN → 200
bash scripts/p3-demo.sh     # 틀린 비밀번호 6번째부터 429, Redis 카운터 확인
bash scripts/p4-2-demo.sh   # 가짜 키와 SQL 인젝션을 넣은 커밋을 gitleaks와 Semgrep이 잡는지
```

테스트는 서비스 폴더에서 실행합니다.

```bash
cd auth-service && ./gradlew test
cd gateway && ./gradlew test
```

쿠버네티스에 올리는 스크립트는 `deploy/local/up.sh`입니다. PC에 클러스터를 만들고 ArgoCD가 배포 설정 저장소의 `deployed` 브랜치를 따라가게 합니다.
