# 설계 결정 기록 (ADR)

> 형식: 날짜 / 어떤 문제였나 / 무엇을 정했나 / 후보는 뭐였나 / 왜 이걸 골랐나 / 버린 것의 대가
> "어떤 문제였나"는 앞선 결정의 어떤 대가가 이 결정을 불렀는지를 적는다. 무엇을 했는지만 적으면 왜 했는지가 남지 않는다.
> **내가 실제로 후보를 저울질해서 고른 것만 적는다.** 클로드가 정해서 통보한 것,
> 아직 배우는 중인 것은 여기에 적지 않는다.

---

## 핵심 결정

## 2026-10-12 — BCrypt 계산은 CPU 개수만큼만 동시에 돌리고, 1초 안에 자리가 안 나면 거절한다

- **어떤 문제였나**: 09-04에 계정 열거를 막으려고 없는 이메일에도 BCrypt를 돌리기로 했다. 그 대가를 재려고 로그인 요청을 초당 60건까지 보내 보니 정상 응답이 37%였고, 원인으로 본 OSIV를 끄자 26%로 오히려 떨어졌다. OSIV가 켜져 있을 때는 DB 연결 10개가 우연히 "BCrypt는 동시에 10개까지"라는 제한 역할을 하고 있었다. 그걸 고치자 200개 넘는 요청이 한꺼번에 계산에 들어가 CPU 2개를 나눠 썼고, 거의 전부 Gateway의 5초 제한을 넘겼다.
- **무엇을 정했나**: BCrypt를 동시에 계산하는 수를 CPU 개수로 제한한다. 이 서버에서는 2다. 자리가 없으면 최대 1초 기다리고, 그래도 없으면 계산하지 않고 503과 Retry-After를 준다. 제한은 로그인 API가 아니라 인코더를 감싸서 건다.
- **후보**: (넘치는 요청) 전부 줄 세워 기다리게 한다 / 짧게 기다리게 하고 넘치면 거절한다. (동시 실행 수) 1 / 2 / 4. (제한을 거는 곳) 로그인 메서드 안 / 인코더.
- **왜 이걸 골랐나**: 전부 줄 세우는 방식은 2차 측정이 이미 그 결과였다. 들어오는 양이 처리량을 넘으면 줄이 끝없이 길어져 전원이 시간 초과가 된다. 동시 실행 수는 1, 2, 4를 재서 정했다. 과부하 구간의 정상 응답이 1은 초당 9~12건, 2는 13~15건, 4는 15~16건이었고 4는 응답이 0.1초 느렸다. BCrypt는 CPU만 쓰는 계산이라 CPU 개수를 넘겨도 처리량이 거의 늘지 않는다. 대기 1초는 Gateway가 포기하는 5초보다 충분히 짧아서, 계산에 들어간 요청은 전부 아직 누군가 기다리는 요청이 된다. 인코더에 건 이유는 회원가입도 같은 인코더로 BCrypt를 돌리기 때문이다. 로그인 메서드에 넣으면 회원가입이 빠진다.
- **버린 것의 대가**: 한계를 넘는 요청은 정상 사용자의 것이라도 503을 받고 다시 시도해야 한다. 이 제한은 공격자와 정상 사용자를 구분하지 못하므로 구분은 Gateway의 IP 기준에 맡겼다. 상한 2에서는 로그인이 몰릴 때 CPU가 전부 BCrypt에 쓰여 다른 API가 느려질 수 있는데, 얼마나 느려지는지는 재지 않았다. 측정은 설정마다 한 번씩만 했다.

## 2026-10-11 — 로그인 제한에 IP 단독 기준을 추가하고, 막힌 요청은 나머지 카운터를 올리지 않는다

- **어떤 문제였나**: 10-05에 로그인 제한 기준을 이메일+IP와 이메일 두 겹으로 정하면서 IP 단독은 뺐다. 그런데 09-04의 계정 열거 방어 때문에 로그인은 없는 이메일에도 BCrypt를 돌린다. 두 결정이 겹치자, 이메일을 매번 바꿔 보내는 요청은 어느 카운터에도 걸리지 않으면서 요청마다 CPU 0.1초를 쓰게 됐다. 부하 실험에서 IP 하나로 초당 60건까지 보내자 정상 응답이 26%로 떨어졌다. BCrypt 동시 실행 상한은 서버를 지키지만 공격자와 정상 사용자를 구분하지 못한다.
- **무엇을 정했나**: 1분에 IP당 30회 기준을 세 번째로 추가한다. IP, 이메일+IP, 이메일 순서로 세고, 한 기준에서 넘으면 거기서 429로 끊고 나머지 기준은 세지 않는다. 로그인에 성공해도 IP 카운터는 지우지 않는다.
- **후보**: (기준) 이메일 5회와 IP 30회 두 개로 단순화 / 기존 두 겹을 두고 IP 30회 추가. (막힌 요청) 계속 센다 / 세지 않는다.
- **왜 이걸 골랐나**: 두 개로 줄이면 단순하고 한 계정에 대한 대입도 1분 5회로 더 엄격하다. 하지만 이메일 단독 카운터는 계정 주인도 같이 쓰는 숫자라, 5로 낮추면 아무나 IP 하나로 5번 틀려 주인을 잠글 수 있다. 그리고 기존 코드를 다시 읽어 보니 막힌 요청도 이메일 카운터를 올리고 있어서, 의도와 달리 IP 하나로 21번만 보내면 주인이 잠겼다. 새 테스트를 기존 방식에 돌리면 실패하는 것으로 확인했다. 막힌 요청을 세지 않으면 통과한 5번만 쌓이므로 IP가 5개 이상 있어야 잠글 수 있다. IP 30회는 IP 하나가 쓸 수 있는 양을 서버가 감당하는 양(추정 분당 900건)의 3%쯤으로 묶는 값이다.
- **버린 것의 대가**: 회사, 학교, 통신사 망처럼 IP 하나 뒤에 수백 명이 있는 곳에서 1분에 30명 넘게 로그인하면 정상 사용자가 막힌다. IP를 여러 개 가진 공격자는 여전히 통과하고, 그때는 BCrypt 동시 실행 상한이 마지막 방어선이다. 로그인마다 Redis 호출이 최대 세 번으로 늘었다.

## 2026-10-08 — 배포는 SSH 대신 SSM 원격 명령으로, 비밀값은 Parameter Store에서 서버가 직접 읽는다

- **무엇을 정했나**: GitHub Actions가 서버에 SSH로 들어가지 않고 AWS SSM Run Command로 "이미지 받아 재시작" 명령을 보낸다. 비밀값은 Terraform이 SSM Parameter Store에 암호화해 넣고, 서버가 부팅 때 IAM 역할로 읽어 .env를 만든다. 서버 방화벽은 8080 전체 공개, 22는 내 IP만.
- **후보**: (배포) SSH로 접속해 명령 실행 / SSM 원격 명령. (비밀값) user_data에 직접 박기 / Parameter Store + 역할. (GitHub 권한) OIDC 임시 자격 / 전용 IAM 사용자 키.
- **왜 이걸 골랐나**: SSH 배포는 GitHub 서버가 들어올 수 있게 22번을 전 세계에 열어야 해서 "22는 내 IP만" 원칙과 충돌한다. user_data는 콘솔과 인스턴스 메타데이터에서 평문으로 읽히므로 비밀값을 넣지 않는다. OIDC가 가장 좋았지만 프로젝트 계정 정책이 신원 공급자 등록을 막아 전용 사용자로 대체하고, 권한을 "이 서버 한 대에 명령 보내기"로만 좁혔다.
- **버린 것의 대가**: GitHub Secrets에 장기 키가 하나 저장된다. 유출돼도 서버를 만들거나 지우진 못하지만, 명령 실행은 가능하므로 주기적 교체가 필요하다. SSM 에이전트와 IAM 역할에 의존하므로 다른 클라우드로 옮기면 배포 방식을 다시 짜야 한다.

## 2026-10-05 — 로그인 제한 기준은 (이메일+IP)와 (이메일) 두 겹, Redis가 죽으면 열어 둔다

- **무엇을 정했나**: 로그인 요청만 제한한다. 1분 고정 창에서 (이메일+IP) 5회, (이메일 단독) 20회. 둘 중 하나라도 넘으면 429 + Retry-After. 로그인에 성공하면 카운터를 지운다. Redis에 접속할 수 없으면 제한 없이 통과시키고(fail-open) 에러 로그를 남긴다.
- **후보**: (기준) IP만 / 이메일만 / 이메일+IP / 두 겹. (Redis 장애 시) 열어 둠(fail-open) / 전부 막음(fail-closed).
- **왜 이걸 골랐나**: IP만으로는 IP를 바꾸는 공격을 못 막고 NAT 뒤 사용자를 오차단한다. 이메일만으로는 공격자가 틀린 비밀번호를 반복해 남의 계정을 잠그는 역공격이 가능하다. 이메일+IP가 정밀하고, 이메일 단독 20회는 IP 분산 공격을 1분 단위로만 늦추는 안전망이다. Redis 장애 시 로그인 전체를 막으면 제한 장치 하나가 서비스 장애가 된다.
- **버린 것의 대가**: 이메일 단독 한도 때문에 1분짜리 역공격(남의 계정에 20회 틀려 1분 잠그기)은 가능하다. fail-open이라 Redis가 죽은 동안은 무차별 대입이 열린다. 고정 창은 창 경계에서 최대 2배(10회)까지 몰릴 수 있다. IP는 `getRemoteAddr()`라 앞에 로드밸런서가 서면 전부 같은 IP로 보인다 (P4에서 X-Forwarded-For 처리 필요).

## 2026-10-02 — 권한(role)은 토큰의 값을 믿고, 요청마다 DB를 다시 보지 않는다

- **무엇을 정했나**: Gateway는 서명 검증을 통과한 토큰의 `role`로 권한을 판단한다. DB 조회는 하지 않는다. role은 갱신(refresh) 때 DB에서 다시 읽어 새 토큰에 넣는다.
- **후보**: (a) 토큰만 믿음 (b) 요청마다 토큰과 DB를 둘 다 확인
- **왜 이걸 골랐나**: (b)는 가장 안전하지만 요청마다 DB 조회가 생겨 JWT를 쓴 이유(Gateway가 DB 없이 혼자 판단)가 사라진다. access token 수명이 1시간이라 권한 변경은 늦어도 1시간 안에 반영된다.
- **버린 것의 대가**: 관리자 권한을 박탈해도 그 사람의 access token이 만료될 때까지(최대 1시간) 관리자 API가 열려 있다. 즉시 차단이 필요한 서비스라면 블랙리스트(Redis)나 민감 작업에 한한 DB 재확인이 필요하다.

## 2026-10-02 — Refresh 재사용 판정에 유예 시간 10초를 둔다

- **무엇을 정했나**: 폐기된 refresh가 폐기 후 10초 안에 다시 오면 거절만 한다. 10초가 지난 뒤에 오면 탈취로 보고 그 사용자의 토큰을 전부 폐기한다.
- **후보**: (a) 유예 없이 항상 전부 폐기 (b) 유예 10초 (c) 재사용 감지 제거
- **왜 이걸 골랐나**: 동시성 실험에서 (a)는 요청 2건만 겹쳐도 매번 강제 로그아웃되는 것을 확인했다(TROUBLES 참고). 훔친 토큰은 보통 바로 쓰이고 정상 사용자는 한참 뒤(다음 갱신 때)에 오므로, 일반적인 탈취는 유예와 무관하게 감지된다.
- **버린 것의 대가**: 공격자와 정상 사용자의 사용이 10초 안에 겹치면 감지하지 못한다. 그리고 재사용 감지 자체의 한계는 그대로다. 정상 사용자가 돌아와야 감지되고, 돌아오지 않으면 공격자가 계속 갱신할 수 있다(최대 세션 기간, 새 기기 알림 등으로 보완해야 함).

## 2026-10-01 — Refresh token: 해시 저장 + 일회용 회전 + 재사용 시 전체 무효화

- **무엇을 정했나**: refresh token은 32바이트 난수. DB에는 SHA-256 해시만 저장. 쓸 때마다 폐기하고 새로 발급(회전). 폐기된 토큰이 다시 오면 그 사용자의 토큰을 전부 폐기하고 재로그인시킨다.
- **후보**: (저장) 서버 저장 안 함(JWT) / 원문 저장 / 해시 저장. (수명) 만료까지 재사용 / 일회용 회전. (저장소) DB 테이블 / Redis.
- **왜 이걸 골랐나**: 서버에 저장해야 로그아웃·탈취 대응이 가능. 해시 저장은 DB 유출 대비. 기기에서 탈취된 경우는 해시로 못 막으므로 회전 + 재사용 감지로 막는다. 저장소는 사용자별 기록이 남는 DB.
- **버린 것의 대가**: 요청마다 DB 조회가 생겨 완전 무상태가 아니다. 응답 유실 후 재시도, 탭 두 개의 동시 갱신 같은 정상 상황도 재사용으로 판정되어 강제 로그아웃된다(유예 시간 없음). 로그아웃한 토큰을 다시 보내도 같은 판정이 난다.

## 2026-09-04 — 로그인 실패 응답은 원인을 구분하지 않는다

- **무엇을 정했나**: 이메일이 없든 비밀번호가 틀리든 동일하게 401 + "이메일 또는 비밀번호가 올바르지 않습니다." 이메일이 없어도 가짜 해시로 BCrypt를 한 번 돌려 응답 시간까지 맞춘다.
- **후보**: (a) "가입되지 않은 이메일" / "비밀번호 틀림" 구분 (b) 동일 메시지
- **왜 이걸 골랐나**: 구분하면 공격자가 가입된 이메일 목록을 무료로 얻는다(계정 열거). 시간 차도 같은 정보를 흘리므로 함께 막는다.
- **버린 것의 대가**: 정상 사용자가 "가입을 안 했던 건지, 비번을 잊은 건지" 스스로 알 수 없어 UX가 조금 나빠진다. 실무에서도 이 대가를 받아들이는 것이 표준.

## 간단 기록 (기본 결정, 한 줄씩)

- 2026-10-12 — Semgrep의 CSRF 룰 제외 옵션을 지웠다. CI를 처음 만들 때 넣었는데, 적어 둔 룰 이름이 Semgrep 룰 저장소에 없는 이름이었고, 이 프로젝트는 Spring Security의 웹 기능을 쓰지 않아 CSRF를 끄는 코드 자체가 없다. 받아들인 경고는 그 줄에만 이유와 함께 예외를 두고 전역으로 끄지 않는다는 원칙에도 어긋났다. 토큰을 쿠키가 아니라 Authorization 헤더로 받으므로 브라우저가 자동으로 실어 보내지 않아 CSRF 대상이 아니다.
