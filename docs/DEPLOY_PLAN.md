# 배포 파이프라인 계획

게이트웨이가 서버에 올라가는 길을 만든다. 변경을 올리면 자동으로 검사하고, 다른 사람이 승인한 것만 배포되고, 누가 무엇을 승인해 무엇이 올라갔는지 기록이 자동으로 남는다. 그다음 그 절차를 일부러 건너뛰어 보고 막히는지 확인한다.

## 명제

승인받은 변경과 실제 배포된 변경이 같다는 것을 증명한다.

## 다루는 규제 요구

| 요구 | 뜻 | 이 프로젝트에서 하는 일 |
|---|---|---|
| 결재 | 권한 있는 사람이 배포를 승인한다 | 올린 사람과 승인한 사람이 달라야 배포된다 |
| 증적 | 누가 언제 무엇을 했는지 기록이 남는다 | 배포 한 건마다 요청자, 승인자, 커밋, 검사 결과, 실제 이미지를 이어서 기록한다 |
| 접근 제어 | 필요한 권한만, 필요한 때만 준다 | CI에 높은 권한을 주지 않고, 오래 쓰는 키를 저장하지 않는다 |

## 진행 순서

우회 시도는 끝에 몰아서 하지 않는다. 각 부분이 돌아가면 바로 그 부분을 뚫어 보고 결과를 기록한다.

### 2. 결재와 증적

- [x] 배포 흐름 만들기: 변경 요청 승인 → 합치기 → 검사 → deployed 브랜치 이동 → 배포
- [x] Go CLI: 배포 직전 검사
  - 승인한 사람이 올린 사람과 다른가
  - 승인받은 커밋과 배포할 커밋이 같은가
  - 보안 검사가 그 커밋에서 통과했는가
- [x] Go CLI: 배포 한 건의 증적 기록 만들기
- [x] Go CLI: 지금 돌고 있는 서비스에서 커밋과 승인자까지 거꾸로 조회하기
- [x] deployed 브랜치 보호 걸기. 태그 대신 브랜치로 바꿨다

### 3. 결재와 증적 우회 시도

| 시도 | 확인하는 것 | GitLab 무료 설정만으로 | 검사를 붙인 뒤 |
|---|---|---|---|
| 승인 없이 합치기 | 승인 없이 배포가 되는가 | 합쳐진다 | 막힘. "승인이 없습니다". deployed가 움직이지 않는다 |
| 본인이 올린 것을 본인이 승인하기 | 올린 사람과 승인자가 분리되는가 | 승인도 되고 합쳐진다 | 막힘. "승인한 사람이 올린 사람 본인뿐입니다" |
| 승인받은 뒤 커밋을 더 얹기 | 승인된 것과 배포된 것이 같은가 | 승인 표시가 유지된 채 합쳐진다 | 막힘. 승인 시각 12:19:20, 커밋이 올라온 시각 12:19:53 |
| 검사 작업이 없는 파이프라인의 이미지 배포하기 | 검사를 거친 것만 배포되는가 | 파이프라인은 성공으로 표시된다 | 막힘. "작업 scan-image가 없습니다" |
| 다이제스트와 커밋을 서로 다른 것으로 적기 | 기록된 이미지와 실제 이미지가 같은가 | 해당 없음 | 막힘. "다이제스트가 다릅니다" |
| 클러스터를 손으로 직접 고치기 | 승인 경로 밖의 변경이 살아남는가 | 해당 없음 | 3초 안에 되돌아간다. ArgoCD selfHeal |
| main에 직접 push하기 | 변경 요청을 건너뛸 수 있는가 | 막힘. 브랜치 보호 | 그대로 |
| deployed에 사람 계정으로 직접 push하기 | 검사 없이 배포가 시작되는가 | 해당 없음 | **뚫림.** 배포 키를 만든 계정은 push가 된다. 미해결. docs/TROUBLES.md |

위 세 줄은 2026-11-24에 변경 요청 5, 6, 7번으로 실제로 합쳐서 확인했다. 세 변경은 main에 남았고 deployed는 움직이지 않았다. 이후 내용을 이전 상태로 되돌리는 변경 요청 8번을 승인받아 합치자 다시 진행됐다.

남은 구멍:

- deployed에 사람 계정으로 직접 push. 위 표.
- 검사 절차 자체가 검사 대상 저장소 안에 있다. 승인 없이 합친 변경이 `scripts/promote.sh`를 고치면 고친 내용대로 실행된다. 시험하지 않았다. 막으려면 파이프라인 정의를 다른 프로젝트에 두어야 한다.
- 저장소 소유자는 보호 설정을 스스로 풀 수 있다. 5번 설정 통제의 주제다.

### 7. AI 얹기: 승인자를 돕는 변경 요약과 그 검증

기본(1~3번)이 돌아간 뒤에 한다. 승인자가 변경 내용을 빨리 파악하게 돕되, AI의 요약을 그대로 믿지 않고 얼마나 믿을 수 있는지 측정한다.

만들 것

- [ ] 변경 요청이 올라오면 파이프라인에서 모델이 변경 내용을 읽는다
- [ ] "무엇이 바뀌었고 어디가 위험한지"를 변경 요청에 댓글로 남긴다
- [ ] 모델은 Claude API를 쓰고, 모델 이름은 설정값으로 분리한다. 코드가 외부 서비스로 나간다는 한계는 문서에 적는다
- [ ] AI 요약은 참고 자료일 뿐이다. 승인은 사람이 하고, CLI 검사는 AI 요약과 무관하게 동작한다

검증할 것

- [ ] 일부러 위험한 변경을 넣은 시험용 변경 요청 묶음 만들기
  - 비밀값을 코드에 넣기
  - 권한 검사를 빼기
  - 보안 검사 단계를 지우기
  - 의존성을 취약한 버전으로 바꾸기
  - 문제없는 변경 (잘못 경고하는지 보기 위한 대조군)
- [ ] 모델이 위험을 짚은 비율과 놓친 비율 측정하기
- [ ] 문제없는 변경에 잘못 경고한 비율 측정하기
- [ ] 같은 변경을 여러 번 돌려 결과가 흔들리는지 보기

| 변경 유형 | 시도 횟수 | 위험을 짚음 | 놓침 |
|---|---|---|---|
| 비밀값 추가 | | | |
| 권한 검사 제거 | | | |
| 보안 검사 단계 제거 | | | |
| 취약한 의존성 | | | |
| 문제없는 변경 (잘못 경고) | | | |

정할 것

| 결정 | 선택지 | 상태 |
|---|---|---|
| 모델 | 로컬 모델 / 외부 API | Claude API로 정함. 측정하려는 것이 요약의 정확도이고, 로컬 모델은 GitLab이 제공하는 실행 환경에서 닿지 않기 때문. |
| 실행 위치 | 파이프라인 안 / 별도 서버 | 미정 |
| 놓친 것이 많을 때 | 요약을 빼기 / 경고 문구를 붙여 유지 / 규칙 기반 검사와 같이 쓰기 | 결과를 보고 정함 |

## 진행 방식

1. 단계마다 문제와 선택지를 먼저 이해한다.
2. 직접 고르고 이유를 내 말로 적는다.
3. 가치가 있는 곳에서는 쉬운 방식을 먼저 해 보고, 문제를 직접 본 뒤 바꾼다.
4. 고른 것과 버린 것을 DECISIONS.md에 남긴다.

## 완성 기준

- 통제마다 어떤 요구를 위한 것인지 연결돼 있다.
- 우회 시도가 스크립트로 남아 누구나 다시 돌려 같은 결과를 본다.
- CI에 높은 권한이 없고 오래 쓰는 키가 저장돼 있지 않다.
- 배포 한 건의 증적을 명령 한 줄로 뽑고, 나중에 덮어쓸 수 없다.
- 버린 선택지가 문서에 있다.
- 로컬 환경이라 못 한 것과 한계를 적었다.

## 확인이 필요한 것

- 무료 등급 API가 변경 요청의 승인자 정보를 주는지
- 승인 후 커밋을 추가했을 때 무료 등급에서 승인이 그대로 남는지
- 검사 단계를 지우는 우회가 실제로 뚫리는지, 뚫리면 어떻게 막을지
