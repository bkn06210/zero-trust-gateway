## 2026-10-11 — 로그인 CPU 고갈: 계정 열거 방어의 대가 측정

### 왜 재는가

로그인 실패 응답을 "이메일 없음"과 "비밀번호 틀림"으로 구분하지 않기로 했고(계정 열거 방어),
응답 시간 차이로도 구분되지 않도록 **없는 이메일에도 가짜 해시로 BCrypt를 한 번 돌린다.**
그 결과 로그인 요청은 계정 존재 여부와 무관하게 요청마다 BCrypt 1회(약 0.1초 CPU)를 쓴다.

한편 요청 제한은 (이메일+IP)와 (이메일) 기준이다. 공격자가 **매번 다른 이메일**로 보내면
어느 카운터에도 걸리지 않고 요청마다 BCrypt를 태울 수 있다.
→ 계정 열거를 막으려던 결정이, 비밀번호를 맞히려는 게 아니라 **CPU를 고갈시켜 정상 로그인을 막는**
   서비스 거부(DoS) 공격을 더 쉽게 만든 것은 아닌가. 그렇다면 어느 정도이고, 보안을 깎지 않고 막을 수 있나.

### 예상 (측정 전에 적음)

- BCrypt 1회 ≈ 0.1초, vCPU 2개 → 이론상 초당 20건 처리가 한계.
- 초당 20건을 넘기면 처리 못 한 요청이 줄을 서고, 대기 시간이 매초 누적되어 응답이 수 초로 늘어난다.
- 톰캣 처리 스레드(기본 200)가 전부 BCrypt에 묶이면, **로그인뿐 아니라 같은 서버의 다른 API
  (토큰 검증만 하는 /users/me)까지 함께 느려진다.** 이것이 공격의 진짜 효과.
- 비교군: 토큰을 들고 하는 /users/me는 BCrypt가 없으므로 훨씬 높은 처리량까지 견딜 것.

### 방법

- 도구: k6 (`observability/loadtest/login.js`). 내 PC에서 공인 IP의 Gateway로 전송.
  필요한 요청량이 초당 수십 건이라 집 회선이 병목이 되지 않는다.
- 시나리오: 매 요청 다른 이메일 + 틀린 비밀번호로 `POST /auth/login`.
  초당 요청 수를 2분 동안 5 → 10 → 20 → 30 → 45 → 60으로 올림.
- 동시에 서버에서 5초 간격으로 CPU 유휴율과 load average 기록, 종료 후 각 서비스 로그 확인.

### 결과

| 항목 | 값 |
|---|---|
| 보낸 요청 | 2,762건. 초당 21.3건은 k6가 **보낸** 양의 평균이지 서버 처리량이 아니다 (아래 정정 참고) |
| 정상 응답(401) | 1,036건, 37.5% |
| 그 외 | 1,726건, 62.5%. 대부분 Gateway의 502 (뒤쪽 응답 5초 초과) |
| 응답 시간 | 중앙값 5.15초, p95 8.92초, 최대 9.7초 |
| CPU 유휴율 | 초당 5~10건 구간 60~70% → 초당 15건 전후에서 0% → 끝까지 0% |
| load average (vCPU 2) | 1.0 → 9.6. 테스트가 끝난 뒤에도 계속 상승 |
| auth-service 로그 | `Connection is not available, request timed out after 30005ms (total=10, active=10, idle=0, waiting=189)` |

### 해석

**정정: 처리 한계를 잘못 읽었다**
- 처음엔 "초당 21.3건 = 서버 처리 한계, 예상 20건과 맞음"으로 해석했다. 틀렸다.
- k6의 ramping-arrival-rate는 서버 응답과 무관하게 정해진 속도로 보낸다. 단계표 합계가 2,850건이고
  보낸 2,762건 + 못 보낸 89건이 정확히 그 값이다. 2,762 ÷ 약 130초 = 21.3. 502도 완료로 센다.
- 그래서 OSIV를 켰을 때와 껐을 때 같은 21.3이 나왔다. 서버 처리량을 재려면 **정상 응답(401)만** 초 단위로 세야 한다.
- 서버 한계의 실제 증거는 CPU 유휴율이 초당 15건 전후에서 0%가 된 것 하나다.
  t3.small의 vCPU 2개가 물리 코어 1개라는 점까지 보면 한계는 초당 15건 전후로 보는 게 측정과 맞다.

**맞은 것**
- 한계를 넘으면 대기가 누적되어 응답이 수 초로 늘어난다.

**예상보다 일찍 온 것**
- CPU는 초당 20건이 아니라 15건 전후에서 포화. t3.small의 vCPU 2개는 물리 코어 1개의 하이퍼스레드 두 개이고,
  BCrypt 외에도 JSON 처리와 수백 개 스레드의 전환 비용이 든다.

**예상하지 못한 것 1: DB 연결 풀 고갈**
- 로그인은 DB를 `findByEmail` 한 번만 쓰는데, 연결 10개가 전부 사용 중이고 189개 요청이 연결을 기다리다 30초 후 실패했다.
- 원인은 Spring Boot의 기본값 **Open Session In View(OSIV)**. 요청이 끝날 때까지 DB 연결을 붙잡아 둔다.
  그래서 로그인은 연결을 잡은 채로 BCrypt를 계산한다. CPU가 포화되어 BCrypt가 수 초 걸리면 연결도 수 초 묶인다.
- 결과적으로 로그인에 부하가 걸리면 **DB를 쓰는 다른 API가 느려지는 게 아니라 실패한다.**
  예상한 "다른 API도 함께 느려진다"는 맞았지만, 원인이 CPU 스레드가 아니라 DB 연결이었다.
- OSIV 경고는 서버 첫 기동 때부터 로그에 찍혀 있었다.

**예상하지 못한 것 2: 버려진 요청을 계속 계산**
- Gateway는 5초가 지나면 포기하고 502를 돌려주지만, auth-service는 그 요청의 BCrypt를 끝까지 계산한다.
  아무도 기다리지 않는 요청에 CPU를 쓰는 것이라, 테스트가 끝난 뒤에도 load average가 계속 올랐다.

### 1차 조치: OSIV 끄기 → 재측정

`spring.jpa.open-in-view=false`로 바꾸고 같은 조건으로 다시 쟀다.

| 항목 | OSIV 켬 | OSIV 끔 |
|---|---|---|
| 보낸 양 평균 (서버와 무관) | 초당 21.3건 | 초당 21.3건 |
| 정상 응답(401) | 37.5% | **26.0%** |
| 응답 시간 중앙값 / p95 | 5.15초 / 8.92초 | 5.18초 / 8.94초 |
| DB 연결 대기 실패 | 수천 건 | **0건** |
| auth-service 스레드 | - | 243개 |

**DB 연결 고갈은 사라졌지만 로그인 성공률은 오히려 떨어졌다.**

**왜 떨어졌나: 연결 풀이 우연히 동시 실행 수를 제한하고 있었다**
- OSIV가 켜져 있을 때는 연결 10개가 BCrypt 계산 내내 묶였다. 그래서 BCrypt를 동시에 계산하는 요청이 최대 10개였고,
  나머지 수백 개는 연결을 기다리며 CPU를 쓰지 않았다. 10개가 CPU 2개를 나눠 쓰니 하나당 약 0.5초에 끝났고,
  그중 상당수가 Gateway의 5초 제한 안에 응답했다.
- OSIV를 끄자 연결은 조회 직후 반납되고, 200개가 넘는 요청이 **한꺼번에** BCrypt에 들어갔다.
  CPU 2개를 200개가 나눠 쓰면 하나당 몫이 1%라 0.1초짜리 계산이 10초 가까이 걸리고, 대부분 5초를 넘겨 502가 됐다.
- 즉 OSIV는 결함이었지만, 그 결함이 **의도치 않은 동시 실행 제한** 역할도 하고 있었다. 결함을 고치자 숨어 있던
  진짜 문제, "BCrypt 동시 실행 수에 상한이 없다"가 드러났다.

**얻은 것**: DB를 쓰는 다른 API가 로그인 부하 때문에 연결을 못 얻어 실패하는 일은 사라졌다(연결 대기 실패 0건).
**남은 것**: 로그인 자체는 CPU를 나눠 쓰는 요청이 너무 많아 거의 전부 시간 초과. 공격자 입장에서는 효과가 그대로다.

### 2차 조치: BCrypt 동시 실행 상한과 IP 기준 → 재측정

**바꾼 것**
- auth-service: BCrypt를 동시에 계산하는 수를 CPU 개수인 2로 제한했다. 자리가 1초 안에 나지 않으면 계산하지 않고 503을 준다.
- Gateway: 로그인 제한에 IP당 1분 30회 기준을 추가했다.

**예상 (측정 전에 적음)**
- 상한 2, IP 기준은 풀어 둠: 초당 5~10건 구간은 전부 401. 한계인 초당 약 15건을 넘는 구간부터는 넘치는 양만 503이 되고,
  초당 60건 구간에서도 401은 초당 약 15건으로 유지된다. 502는 0건.
- 응답 시간: 한계를 넘는 구간에서는 401이든 503이든 줄에서 1초 가까이 기다린다. 401은 1.1초 안팎, 503은 1초 안팎. 5초를 넘는 응답은 없다.
- 전체 정상 응답 비율은 45% 안팎. 서버가 감당하는 양 자체가 초당 약 15건이라 100%가 될 수는 없다.
  달라지는 것은 비율보다, 한계를 넘어도 처리량이 무너지지 않는다는 점과 실패가 빨라진다는 점이다.
- 상한 1: 처리량이 2일 때보다 낮다. 다만 vCPU 2개가 물리 코어 1개라 절반까지 떨어지지는 않는다.
- 상한 4: 처리량은 2와 같고 401 응답 시간만 늘어난다.
- 기본 설정인 상한 2, IP 30회: 한 PC에서 보내므로 1분에 30건만 통과하고 나머지는 Gateway가 429로 끊는다. BCrypt가 거의 돌지 않아 CPU는 한가하다.

**방법**
- 1, 2차와 같은 스크립트. k6가 남긴 요청별 기록을 보낸 시각 기준으로 20초 단계별, 응답 코드별로 센다.
- 상한은 환경변수로 1, 2, 4를 바꿔 가며 잰다. IP 기준은 재는 동안만 풀어 두고 끝나면 되돌린다.
- 설정마다 한 번씩만 쟀다. 초당 1건 안팎의 차이는 오차일 수 있다.

**결과 1: 상한 2, IP 기준은 풀어 둠**

| 항목 | 1차 OSIV 켬 | 2차 OSIV 끔 | 3차 상한 2 |
|---|---|---|---|
| 정상 응답(401) | 37.5% | 26.0% | **49.0%** (1,395건) |
| 실패의 종류 | 대부분 502, 5초 뒤 | 대부분 502, 5초 뒤 | 전부 503, 약 1.2초 뒤. **502는 0건** |
| 응답 시간 중앙값 / p95 / 최대 | 5.15초 / 8.92초 / 9.7초 | 5.18초 / 8.94초 | **1.17초 / 1.35초 / 2.03초** |
| DB 연결 대기 실패 | 수천 건 | 0건 | 0건 |
| 테스트가 끝난 뒤 | load average가 계속 상승 | - | 5초 뒤 CPU 유휴율 78%, 10초 뒤 97% |

|---|---|
| 응답 2,850건 | 429 2,790건(97.9%), 401 51건, 503 9건 |
| 응답 시간 중앙값 / p95 | 0.16초 / 0.28초 |

**예상과 비교**
- 맞은 것: 502가 사라졌고 5초를 넘는 응답이 없다. 한계를 넘어도 정상 응답이 초당 13~15건으로 유지된다. 전체 비율은 예상 45%에 실측 49%.
- 맞은 것: 상한 1은 2보다 낮지만 절반은 아니다. 초당 약 11.6건으로 2일 때의 77%. 대신 CPU가 20~30% 남는다.
- 조금 다른 것: 응답 시간. 401은 1.1초 예상에 1.28초, 503은 1초 예상에 1.17초. 한가할 때의 401이 0.24초이므로 한국과 시드니 사이 왕복 시간이 0.15초쯤 깔려 있다.
- 조금 다른 것: 상한 2에서 보내는 양이 늘수록 초당 401이 15.2에서 12.8로 줄었다. 거절하는 요청도 Gateway와 auth-service에서 CPU를 쓰기 때문으로 추정한다.
- 다른 것: 상한 4는 처리량이 2와 같을 것으로 봤는데 4~13% 높게 나왔다. 응답 시간이 0.1초 늘어난 것은 예상대로다.
  한 번씩만 잰 오차일 수도 있고, 계산 스레드가 많을수록 같은 서버의 다른 프로그램보다 CPU를 더 많이 가져가서일 수도 있다. 확인하지 않았다.
- 예상하지 못한 것: 기본 설정에서 503이 9건 나왔다. 고정 창이라 1분이 지나 카운터가 0이 되는 순간 30건이 한꺼번에 통과했고,
  그중 21건은 처리되고 9건은 1초 안에 자리를 못 얻었다. IP 기준이 흘려보낸 순간 몰림을 BCrypt 상한이 받아낸 것이다.
  10-05에 고정 창을 고르며 적어 둔 "창 경계에서 몰린다"는 대가를 실제로 본 셈이다.

**해석**
- 정상 응답 비율이 26%에서 49%로 올랐지만 핵심은 비율이 아니다. 서버가 감당하는 양이 초당 약 15건이라 그보다 많이 오면 어차피 다 받을 수 없다.
  달라진 것은 **한계를 넘어도 그 15건을 계속 처리한다**는 점이다. 2차에서는 한계를 넘는 순간 거의 전부가 시간 초과였다.
- 실패가 "5초 기다린 뒤 502"에서 "1.2초 뒤 503과 Retry-After"로 바뀌었다. 실패한 쪽이 빨리 알고 다시 시도할 수 있다.
- 테스트가 끝나자 서버가 바로 한가해졌다. 아무도 기다리지 않는 요청을 계산하던 문제가 사라졌다.
- 요청 폭주를 실제로 끊는 것은 IP 기준이다. 기본 설정에서는 같은 양을 보내도 CPU가 85% 넘게 남았다.
  BCrypt 상한은 IP 기준을 통과한 양이 서버를 넘칠 때의 마지막 방어선이다.

**재지 않은 것**
- 로그인 폭주 중에 다른 API의 응답 시간. 처음 예상에 있던 "다른 API까지 느려진다"는 아직 직접 확인하지 못했다.
- IP가 여러 개인 경우. 측정은 PC 한 대에서 했다.

### 결정

- **BCrypt 동시 실행 상한은 CPU 개수로 한다.** 이 서버에서는 2다. 1은 처리량이 4분의 3 수준이고, 4는 처리량이 거의 같은데 응답이 0.1초 느렸다.
  숫자를 코드에 적지 않고 CPU 개수를 읽게 해서, 서버 사양이 바뀌면 따라가게 했다.
- **자리를 기다리는 시간은 최대 1초.** Gateway가 5초에 포기하므로 그보다 충분히 짧아야 버려진 요청을 계산하지 않는다.
- **로그인 제한에 IP당 1분 30회를 추가한다.** 요청 폭주를 실제로 끊는 것은 이 기준이고, BCrypt 상한은 그걸 통과한 양이 넘칠 때의 마지막 방어선이다.
- **계정 열거 방어는 그대로 둔다.** 없는 이메일에도 BCrypt를 돌리는 결정을 되돌리지 않고, 그 대가만 줄였다.
- **남은 것**: IP가 여러 개인 폭주는 IP 기준을 통과한다. 그때 BCrypt 상한이 서버는 지키지만 정상 사용자의 로그인도 함께 503을 받는다.
  CAPTCHA나 WAF가 맡는 영역이고 이 프로젝트에서는 하지 않았다.
