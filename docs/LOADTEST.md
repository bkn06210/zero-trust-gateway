## 2026-10-11 — 로그인 CPU 고갈: 계정 열거 방어의 대가 측정

### 왜 재는가

로그인 실패 응답을 "이메일 없음"과 "비밀번호 틀림"으로 구분하지 않기로 했고(계정 열거 방어),
응답 시간 차이로도 구분되지 않도록 **없는 이메일에도 가짜 해시로 BCrypt를 한 번 돌린다.**
그 결과 로그인 요청은 계정 존재 여부와 무관하게 요청마다 BCrypt 1회(약 0.1초 CPU)를 쓴다.

한편 요청 제한은 (이메일+IP)와 (이메일) 기준이다. 공격자가 **매번 다른 이메일**로 보내면
어느 카운터에도 걸리지 않고 요청마다 BCrypt를 태울 수 있다.
→ 계정 열거를 막으려던 결정이, 비밀번호를 맞히려는 게 아니라 **CPU를 고갈시켜 정상 로그인을 막는**
   서비스 거부(DoS) 공격을 더 쉽게 만든 것은 아닌가. 그렇다면 어느 정도이고, 보안을 깎지 않고 막을 수 있나.

### 예상 (측정 전에 적음)

- BCrypt 1회 ≈ 0.1초, vCPU 2개 → 이론상 초당 20건 처리가 한계.
- 초당 20건을 넘기면 처리 못 한 요청이 줄을 서고, 대기 시간이 매초 누적되어 응답이 수 초로 늘어난다.
- 톰캣 처리 스레드(기본 200)가 전부 BCrypt에 묶이면, **로그인뿐 아니라 같은 서버의 다른 API
  (토큰 검증만 하는 /users/me)까지 함께 느려진다.** 이것이 공격의 진짜 효과.
- 비교군: 토큰을 들고 하는 /users/me는 BCrypt가 없으므로 훨씬 높은 처리량까지 견딜 것.

### 방법

- 도구: k6 (`observability/loadtest/login.js`). 내 PC에서 공인 IP의 Gateway로 전송.
  필요한 요청량이 초당 수십 건이라 집 회선이 병목이 되지 않는다.
- 시나리오: 매 요청 다른 이메일 + 틀린 비밀번호로 `POST /auth/login`.
  초당 요청 수를 2분 동안 5 → 10 → 20 → 30 → 45 → 60으로 올림.
- 동시에 서버에서 5초 간격으로 CPU 유휴율과 load average 기록, 종료 후 각 서비스 로그 확인.

### 결과

| 항목 | 값 |
|---|---|
| 완료된 요청 | 2,762건, 평균 처리량 초당 21.3건 |
| 정상 응답(401) | 1,036건, 37.5% |
| 그 외 | 1,726건, 62.5%. 대부분 Gateway의 502 (뒤쪽 응답 5초 초과) |
| 응답 시간 | 중앙값 5.15초, p95 8.92초, 최대 9.7초 |

### 해석

**예상과 맞은 것**
- 처리 한계는 초당 약 20건(실측 평균 21건). 넘으면 대기가 누적되어 응답이 수 초로 늘어남.

**예상보다 일찍 온 것**
- CPU는 초당 20건이 아니라 15건 전후에서 포화. t3.small의 vCPU 2개는 물리 코어 1개의 하이퍼스레드 두 개이고,
  BCrypt 외에도 JSON 처리와 수백 개 스레드의 전환 비용이 든다.

**예상하지 못한 것 1: DB 연결 풀 고갈**
- 로그인은 DB를 `findByEmail` 한 번만 쓰는데, 연결 10개가 전부 사용 중이고 189개 요청이 연결을 기다리다 30초 후 실패했다.
- 원인은 Spring Boot의 기본값 **Open Session In View(OSIV)**. 요청이 끝날 때까지 DB 연결을 붙잡아 둔다.
  그래서 로그인은 연결을 잡은 채로 BCrypt를 계산한다. CPU가 포화되어 BCrypt가 수 초 걸리면 연결도 수 초 묶인다.
- 결과적으로 로그인에 부하가 걸리면 **DB를 쓰는 다른 API가 느려지는 게 아니라 실패한다.**
  예상한 "다른 API도 함께 느려진다"는 맞았지만, 원인이 CPU 스레드가 아니라 DB 연결이었다.
- OSIV 경고는 서버 첫 기동 때부터 로그에 찍혀 있었다.

**예상하지 못한 것 2: 버려진 요청을 계속 계산**
- Gateway는 5초가 지나면 포기하고 502를 돌려주지만, auth-service는 그 요청의 BCrypt를 끝까지 계산한다.
  아무도 기다리지 않는 요청에 CPU를 쓰는 것이라, 테스트가 끝난 뒤에도 load average가 계속 올랐다.
