## 2026-10-12 — 비밀값 검사를 통과한 Terraform 계획 파일에 비밀값이 평문으로 들어 있었다

- **증상**: CI에 Terraform 검사가 빠져 있는지 보려고 `infra/` 아래 저장소에 올라간 파일 목록을 확인하다가 `plan.out`을 발견했다. 10-08의 배포 관련 커밋에 다른 파일 세 개와 함께 섞여 들어간 Terraform 계획 파일이다. 압축을 풀어 보니 JWT 비밀키, DB 비밀번호, 관리자 비밀번호가 평문으로 있었고, 해시를 비교하니 서버가 쓰고 있는 JWT 비밀키와 같았다. 공개 저장소에 나흘 동안 있었고, 그동안 CI의 gitleaks는 매번 통과했다.
- **처음 세운 가설**: 비밀값은 세 겹으로 막혀 있다고 믿고 있었다. 값이 적힌 `terraform.tfvars`는 .gitignore에 있고, Terraform 변수에는 `sensitive`를 붙였고, CI에서 gitleaks가 커밋 이력 전체를 본다.
- **틀린 이유**: 세 겹 모두 이 파일을 비켜 갔다. `sensitive`는 화면 출력만 가릴 뿐 계획 파일에는 값이 그대로 저장된다. .gitignore에는 변수 파일과 상태 파일만 있고 계획 파일 종류가 빠져 있었다. gitleaks는 글자로 된 비밀값 모양을 찾는데 계획 파일은 압축 파일이라 안을 보지 못한다.
- **실제 원인**: `terraform plan -out`으로 만든 파일을 인프라 폴더에 둔 채, 커밋에 무엇이 들어가는지 확인하지 않고 올렸다. 도구가 막아 줄 것이라 믿고 사람이 하는 확인을 건너뛴 것이다.
- **해결**: 파일을 지우는 것으로는 부족하다. 이미 공개된 값은 되돌릴 수 없으므로 유출된 것으로 보고 교체했다. 새 값을 만들어 Parameter Store에 넣고, 서버는 값만 바꾸지 않고 Terraform으로 새로 만들어 부팅하면서 새 값을 읽게 했다. 교체 명령부터 새 서버가 응답하기까지 3분쯤 걸렸고, 새 서버가 옛 키를 쓰지 않는 것을 해시 비교로 확인했다. 저장소에서 파일을 지우고 .gitignore에 계획 파일 종류를 추가했다. CI에는 올라오면 안 되는 파일을 이름으로 막는 검사를 넣었고, 이 검사를 유출 당시의 파일 목록에 돌리면 `plan.out`이 걸리는 것을 확인했다.
- **피해 조사**: 악용 흔적은 찾지 못했다. 관리자 계정으로 만들어진 로그인 세션이 없었고, 지표에 관리자 API 호출이 없었다. 관리자 API는 사용자 목록 조회 하나뿐이고 서버에는 테스트 계정만 있었다. 계획 파일은 서버를 만들기 전의 최초 계획이라 AWS 배포 키는 들어 있지 않았다. 흔적이 없다는 것이지 접근이 없었다는 증명은 아니다.
- **남은 대가**: 파일은 과거 커밋에 남아 있다. 값을 교체했으므로 쓸모는 없어졌다. 관리자 이메일과 SSH를 허용한 IP는 교체할 수 없는 정보인데 함께 들어 있었다. 서버를 새로 만들면서 지표 기록 나흘치를 잃어 부하 실험 일부를 다시 쟀다.
- **배운 것**: 스캐너가 통과했다는 것은 스캐너가 볼 수 있는 범위에서 없었다는 뜻일 뿐이다. 압축 파일, 바이너리, 상태 파일처럼 스캐너가 못 보는 종류는 내용이 아니라 이름으로 막아야 한다. 커밋하기 전에 들어가는 파일 목록을 직접 본다. 비밀값이 한 번이라도 공개되면 삭제가 아니라 교체가 답이고, 서버를 코드로 만들어 두면 교체가 몇 분짜리 일이 된다.

## 2026-10-11 — DB 연결 풀 고갈을 고쳤더니 로그인 성공률이 37%에서 26%로 떨어졌다

- **증상**: 내 서버에 로그인 요청을 초당 5건에서 60건까지 올려 보내자 정상 응답이 37.5%였고 나머지는 대부분 Gateway의 502였다. auth-service 로그에는 `Connection is not available, request timed out after 30005ms (total=10, active=10, idle=0, waiting=189)`가 찍혔다. 로그인은 DB를 조회 한 번만 쓰는데 연결 10개가 전부 묶여 있었다.
- **처음 세운 가설**: 원인은 Spring Boot 기본값인 OSIV다. 요청이 끝날 때까지 DB 연결을 쥐고 있어서 BCrypt를 계산하는 동안에도 연결이 묶인다. OSIV를 끄면 연결이 조회 직후 반납되어 성공률이 오를 것이다.
- **틀린 이유**: OSIV를 끄고 같은 조건으로 다시 재니 연결 대기 실패는 0건이 됐지만 정상 응답은 26.0%로 오히려 떨어졌다. 연결 고갈은 드러난 증상이었을 뿐이고, 그 고갈이 다른 문제를 가려 주고 있었다.
- **실제 원인**: BCrypt를 동시에 계산하는 수에 상한이 없었다. OSIV가 켜져 있을 때는 연결을 쥔 10개만 계산하고 나머지는 연결을 기다리며 CPU를 쓰지 않았다. 연결 풀이 우연히 동시 실행 제한 역할을 한 것이다. OSIV를 끄자 200개 넘는 요청이 한꺼번에 계산에 들어가 CPU 2개를 나눠 썼고, 0.1초짜리 계산이 10초 가까이 걸려 대부분 Gateway의 5초 제한을 넘겼다. Gateway가 포기한 요청도 auth-service는 끝까지 계산하고 있었다.
- **해결**: 우연히 있던 제한을 의도한 제한으로 다시 만들었다. BCrypt 인코더를 세마포어로 감싸 CPU 개수인 2개까지만 동시에 계산하고, 1초 안에 자리가 안 나면 계산 없이 503을 준다. 세 번째 측정에서 정상 응답은 49.0%, 502는 0건, 응답 시간 중앙값은 5.18초에서 1.17초가 됐다. 한계를 넘는 구간에서도 정상 응답이 초당 13~15건으로 유지됐다. 여기에 Gateway의 IP당 1분 30회 기준을 더하자 같은 양을 보내도 97.9%가 입구에서 끊기고 CPU는 85% 넘게 남았다. 전체 수치는 LOADTEST.md에 있다.
- **남은 대가**: 서버가 감당하는 양은 그대로 초당 약 15건이다. IP가 여러 개인 폭주는 IP 기준을 통과하고, 그때는 정상 사용자의 로그인도 503을 받는다.
- **배운 것**: 결함 하나를 고쳤는데 지표가 나빠지면, 그 결함이 다른 문제를 가리고 있었을 수 있다. 그래서 고친 뒤에는 같은 조건으로 다시 잰다. 측정 도구가 내는 숫자가 무엇을 센 것인지도 먼저 확인해야 한다. 처음에는 k6가 보낸 양의 평균인 초당 21.3건을 서버의 처리 한계로 잘못 읽었고, OSIV를 켰을 때와 껐을 때 같은 숫자가 나온 것이 단서였다. CPU만 쓰는 작업은 동시에 돌리는 수를 CPU 개수로 묶어야 하고, 넘치는 요청은 줄 세우기보다 빨리 거절하는 쪽이 처리량을 지킨다.

## 2026-10-08 — 유료 플랜으로 바꿔도 EC2가 계속 거부됐다. 원인은 플랜이 아니라 리전이었다

- **증상**: Terraform plan에서 `ec2:DescribeVpcs`가 `explicit deny in a service control policy`로 거부. 모든 리전에서 같았고 SSM, Lambda, ECS도 거부. 계정은 2025년 이후의 새 가입 구조로 만든 것.
- **처음 세운 가설**: 신규 계정의 "무료 플랜" 제한이다. Free Tier API로 확인하니 실제로 `accountPlanType = FREE`였고, 유료 플랜으로 전환하면 풀릴 것이라 봤다.
- **틀린 이유**: 유료로 전환해 `PAID`가 된 뒤에도 몇 시간 동안 같은 거부가 계속됐다. 정책을 건 조직의 관리 계정을 조회하니 AWS가 아니라 내 gmail 주소였다. 즉 "AWS가 건 무료 플랜 제한"이 아니라 "내 계정 구조 안의 정책"이었다.
- **실제 원인**: 새 가입 구조는 관리 계정, 신원 계정, 프로젝트 계정 세 개를 만들고 사용자는 프로젝트 계정만 쓴다. 프로젝트 계정에는 정책 네 개가 걸리는데 그중 **단일 리전 제한 정책은 유료 전환 뒤에도 남는다.** 모든 리전을 돌며 `DescribeVpcs`를 호출해 보니 허용된 곳은 시드니(ap-southeast-2) 하나였다. 가입 때 리전을 고른 적이 없는데 AWS가 배정한 것이다. IAM 정책 시뮬레이터로 `AllowedByOrganizations = False`를 확인해 IAM 권한 문제는 배제했다.
- **해결**: Terraform 리전을 시드니로 바꾸고 apply. 13개 리소스 생성, 90초 뒤 공인 IP에서 응답. 같은 구조의 정책이 OIDC 신원 공급자 등록도 막아서, GitHub 배포 권한은 OIDC 대신 "이 서버에 명령 보내기"만 허용한 전용 IAM 사용자로 대체했다.
- **배운 것**: 거부 메시지의 정책 ARN과 조직 ID를 읽으면 "누가 막았는지"가 나온다. 가설을 세웠으면 전환 후 기다리지 말고 API로 상태를 직접 확인한다. 권한 문제는 정책 시뮬레이터로 IAM과 조직 정책을 분리해서 본다. 플랫폼이 새로 바뀐 영역은 문서를 먼저 찾는 게 빠르다.

## 2026-10-05 — CI 첫 실행에서 이미지 스캔이 CRITICAL 4건을 잡았는데, 최신 Spring Boot로 올려도 안 고쳐졌다

- **증상**: GitHub Actions에 Trivy 이미지 스캔을 붙인 첫 실행에서 두 서비스 모두 실패. 우리 코드가 아니라 jar 안의 라이브러리였다. Tomcat 11.0.22에 인증 우회 CRITICAL 3건(CVE-2026-65182, 65905, 68525), Netty 4.2.15에 CRITICAL 1건, Jackson에 DoS HIGH 10건.
- **처음 세운 가설**: Spring Boot 패치 버전을 올리면 Boot가 관리하는 라이브러리 버전이 따라 올라가서 해결될 것이다.
- **틀린 이유**: Maven Central의 Boot 4.0.8 의존성 목록을 직접 확인하니 Netty는 4.2.17로 고쳐졌지만 Tomcat은 11.0.24, Jackson은 3.1.5였다. Trivy가 요구한 고쳐진 버전은 Tomcat 11.0.25, Jackson 3.1.7. 다음 마이너인 4.1.1도 같았다. Boot 릴리스가 라이브러리 패치를 아직 따라잡지 못한 상태였다.
- **실제 원인**: Boot의 의존성 관리(BOM)는 "Boot가 테스트한 버전 조합"이지 "취약점이 없는 최신"이 아니다. 라이브러리 취약점 공개와 Boot 릴리스 사이에는 항상 시차가 있다.
- **해결**: Boot는 4.0.8로 올리고, Tomcat과 Jackson은 `ext['tomcat.version']`, `ext['jackson-bom.version']`으로 Boot가 정한 버전을 덮어썼다. 고쳐진 버전이 실제로 배포되어 있는지 Maven Central에서 먼저 확인했다. 두 서비스 테스트 34건 통과 후 push → CI 전부 통과. Boot가 따라잡으면 지우도록 주석으로 남겼다.
- **배운 것**: "프레임워크 최신 버전 = 안전"이 아니다. 스캐너가 알려준 고쳐진 버전과 프레임워크가 관리하는 버전을 따로 확인해야 하고, 둘이 다르면 개별 덮어쓰기가 필요하다. 이미지 스캔을 CI에 넣지 않았으면 인증 우회 취약점이 있는 Tomcat으로 배포했을 것이다.

## 2026-10-02 — 동시에 갱신하면 "성공" 응답으로 이미 폐기된 refresh 토큰이 나간다

- **증상**: 같은 refresh 토큰으로 갱신 요청을 동시에 보내면 한 건은 200과 새 토큰을 받고 나머지는 401. 응답만 보면 정상이다. 그런데 직후 DB를 보면 그 사용자의 살아 있는 토큰이 0개. 200으로 받은 새 토큰이 이미 폐기되어 있어, 다음 갱신에서 사용자가 이유 없이 로그아웃된다. 동시 20건에서 4회 중 4회, 동시 2건(브라우저 탭 두 개 수준)에서도 5회 중 5회 재현.
- **처음 세운 가설**: 설계 단계에서 "탭 겹침이나 재시도는 드문 경우이니, 재사용으로 판정해 전부 폐기해도 감수할 만하다"고 봤다. 기존 테스트(순차 호출, 상태 코드 확인)도 전부 통과하고 있었다.
- **틀린 이유**: 드문 경우가 아니었다. 2건만 겹쳐도 매번 발생했다. 그리고 손해가 "늦은 요청이 거절된다"가 아니라 "먼저 성공한 요청이 받은 토큰까지 죽는다"였다. 상태 코드만 보는 테스트로는 보이지 않았고, 동시 요청 후 DB의 살아 있는 토큰 수를 세어보고서야 드러났다.
- **실제 원인**: 요청 A가 옛 토큰을 폐기하고 새 토큰을 저장한 뒤, 요청 B가 "이미 폐기된 토큰"을 만나 재사용으로 판정하고 그 사용자의 토큰을 전부 폐기한다. A가 방금 만든 새 토큰도 거기 포함된다. 서버가 "탭 겹침(0.01초 차이)"과 "탈취(몇 분~몇 시간 뒤)"를 구분할 정보를 갖고 있지 않았다.
- **해결**: 폐기 시각(`revoked_at`)을 기록하고 유예 시간(10초)을 뒀다. 폐기 직후에 같은 토큰이 다시 오면 거절만 하고 다른 토큰은 건드리지 않는다. 유예 시간이 지난 뒤에 오면 기존대로 전부 폐기한다. 유예 안의 요청에도 새 토큰은 주지 않으므로 그 틈에 끼어든 쪽이 얻는 것은 없다. 테스트를 먼저 "살아 있는 토큰이 1개이고 그 토큰으로 다시 갱신된다"로 바꿔 실패를 확인한 뒤 수정했고, 5회 반복 모두 통과.
- **남은 대가**: 공격자가 먼저 쓰고 10초 안에 정상 사용자가 쓰면 그 순간에는 탈취를 감지하지 못한다. 유예를 늘릴수록 이 구멍이 커진다.
- **배운 것**: 동시성 문제는 순차 테스트와 상태 코드만으로는 드러나지 않는다. 요청을 실제로 동시에 쏘고, 응답이 아니라 끝난 뒤의 저장 상태를 검증해야 한다. "드물 것이다"는 측정하기 전까지 가정일 뿐이다.
